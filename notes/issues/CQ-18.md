## Problem

**CQ-18. Blackjack's Deal/Hit/Stand/Split buttons hardcode untokenized hex.**

An `.impeccable` whole-app critique (same tool/gap as [[BUG-9]]) flagged
these buttons as violating DESIGN.md's "Table Overrides Chrome" rule, and
suggested re-deriving them from `getTableTheme("blackjack")`. Two of the
critique's supporting details were wrong even for the code as it stood
(cited hex `#e94560`, actual was `#cc2222`; claimed the label font was
`scaleFont(12)`, actual was already `scaleFont(16)`).

## Verified/Fixed 2026-08-18

Investigated re-aligning to the table-theme system before touching anything.
`getTableTheme()` only exposes 2 fields (`table`, `accent`) — no 4-color
scheme exists anywhere to derive Deal/Hit/Stand/Split from. Checked every
other multi-button game screen (Poker, Rummy, Conquián, Go Fish): all of them
also hardcode their own action-button colors independently, with zero
derivation from `getTableTheme()`. Re-theming Blackjack alone would invent a
one-off pattern nowhere else in the app and make it *more* inconsistent with
its siblings, not less.

Decided (with Pedro) to tokenize instead of re-theme: named the 4 raw hex
values as module constants (`BJ_DEAL_RED`, `BJ_STAND_BLUE`, `BJ_SPLIT_PURPLE`)
in `GameScreen.js`, zero visual change. Kept the existing in-code comment
explaining the deliberate choice to avoid colliding with Home's `brandRed`.
Also removed `const ACCENT = getTableTheme("blackjack").accent` — declared
but never referenced anywhere in the file.

**Not done, and not recommended as a quick follow-up:** app-wide, every
multi-button game screen has this same untokenized-action-color pattern
(Poker's `callBtn`, Rummy's `takeButton`/`drawButton`/etc., Conquián's
`actionBtn`/etc., Go Fish's `askBtn`). That's a real, bigger, cross-file
consistency gap — worth its own ticket if it's ever prioritized, not
something to fold into a single-screen polish pass.

Commit `4a1adc6`.
