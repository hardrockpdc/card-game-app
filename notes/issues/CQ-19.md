## Problem

`.gitattributes` declares `*.js text eol=crlf` and `*.md text eol=lf`, but the files were
never renormalized after it was added. The committed blobs still carry CRLF, so git wants
to rewrite every text file's stored line endings. `git status` normally hides this behind
the index stat cache; any operation that invalidates that cache (`git add --renormalize`,
some checkouts) makes all 123 files appear modified at once.

Nothing is actually wrong with the working tree. File contents and mtimes are untouched —
the diff is line endings only.

## Why it matters

Two live hazards:

1. **`git add -A` would sweep all 123 files into one churn commit.** Use explicit paths in
   this repo until this is fixed.
2. `git checkout -- <file>` does not clear the dirty state for an affected file, which
   makes it look like a tool is rewriting the file in the background. It isn't.

## Fix

Fixed in `8183437` with the git-prescribed one-time `git add --renormalize .`, 122 files
in one commit. Both open questions resolved:

- **`archive/PROJECT_NOTES.md`** is marked `archive/PROJECT_NOTES.md -text` in
  `.gitattributes` instead of being renormalized. Unsetting the attribute stops git
  converting it at all, so the frozen file stays byte-identical *and* stops showing as
  modified — better than a pathspec exclusion, which would have left it dirty forever. The
  line sits below `*.md text eol=lf` because last match wins per attribute;
  `git check-attr text archive/PROJECT_NOTES.md` reports `unset`.
- **The Prettier/CRLF incident cannot recur.** Verified with `git checkout-index --prefix`
  into a scratch directory: `App.js` smudges to CRLF per `eol=crlf`, `Product.md` and
  `database.rules.json` to LF, and the stored `App.js` blob is LF.

No content changed — `git diff --cached --ignore-cr-at-eol` was empty across all 122 files
before committing. `npm test` green (577/577), though that is a sanity canary rather than
evidence: `--renormalize` writes to the index only and never touches working-tree files.
