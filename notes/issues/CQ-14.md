## Problem

## CQ-14. Save effects use raw JSON.parse without schema validation

**Effort:** 1-2 hours (post-launch)
**Risk if ignored:** Older saves silently break when the schema changes; user sees "couldn't load save" or game starts fresh

### What's happening

`game/gameSaves.js`:

```javascript
export async function loadGame(gameKey) {
  try {
    const raw = await AsyncStorage.getItem(gameKey);
    if (raw === null) return null;
    return JSON.parse(raw);
  } catch (err) {
    warn("[gameSaves] load failed — wiping corrupted save:", err);
    await AsyncStorage.removeItem(gameKey).catch(() => {});
    return null;
  }
}
```

This is fine when the save schema is stable. But if you add a new field to one of the game states in a future update (say, `gameState.metadata`), and a user loads a v1 save, the parsed object will be missing that field. Code that assumes `gameState.metadata` exists will crash or behave incorrectly.

### Why this matters

This is the same problem as IMP-7 (Schema versioning for saves). They're related:
- CQ-14 is the *detection* — notice when a save is from an older schema
- IMP-7 is the *handling* — version saves with `{ schemaVersion: 1, ... }`

For v1.0 with no migrations, you don't need either. For v1.1 onward, both become important.

### The fix (deferred to v1.1)

Combine with IMP-7. When you do a release that changes any save schema, bump `schemaVersion` and add a migration path. Loads should check the version and either migrate or wipe with a friendly message.

## Verified 2026-08-15

Claim checks out fully against today's code and a real commit. The raw unguarded
`JSON.parse` shown above no longer exists — `loadGame` (`game/gameSaves.js:80-87`) now
delegates to a shared `readValidSave()` helper (`:53-78`), which parses inside try/catch
and wipes on corrupt JSON (`:58-64`), treats an old unwrapped save (no `__v` field) as
version 1 for backward compatibility (`:66-68`), and on any version mismatch warns,
removes the AsyncStorage entry, and returns `null` (`:71-75`). `saveGame` (`:30-48`)
writes `{ __v: SAVE_VERSION, data: state }`, confirming the wrapper on the write side.
`hasSave` (`:101-108`) also delegates to `readValidSave`, so it no longer does a raw
existence check — it correctly reports "no save" for anything `loadGame` would reject,
keeping the resume prompt consistent.

Commit `ba929a5` is genuine, touches exactly `game/gameSaves.js` and
`__tests__/gameSaves.test.js`. Tests confirmed present and passing:
`__tests__/gameSaves.test.js:35` ("a save is written with a version wrapper"), `:42` ("a
legacy unwrapped save still loads, treated as v1"), plus a version-mismatch-discard case
at line 51.

**Cross-reference worth carrying forward:** IMP-7 ("Schema versioning for saves," the
paired "handling" ticket this one is explicitly linked to) is still listed unchecked in
the archive, and not currently in any verification batch. Functionally, this fix *is* a
real, working schema-versioning mechanism — most of what IMP-7 asked for (bump version,
detect mismatch, avoid crash) — but it does not provide an actual migration path: a
mismatched save is wiped, not transformed. IMP-7 is effectively subsumed for the
"detect and safely discard" case, not for "preserve old data via migration," if that's
ever wanted. No fix needed for CQ-14 itself.
